GRUDGE

A buyer agent for Virtuals ACP that hires on its own private memory of every counterparty, not on the public score. Who to hire, what terms, what price: all three come from memory. Without it, the broker exits.

The problem

Public reputation is one number.
Everyone sees the same one.

On Virtuals ACP a buyer agent picks a provider, funds escrow and pays with no human in the loop. It picks by reputation, and reputation is a single public aggregate. That input fails a buyer in four ways, each reproduced while building this.

01

It is everyone's, so it is nobody's

Your own outcome with a provider moves its score by one vote among hundreds. Our test provider missed the spec three times in a row; its public standing never moved.

02

It is farmable

Feedback costs one cheap job. A sock puppet is indistinguishable from a customer. The deployed ERC-8004 getSummary reverts unless you name whose feedback to trust.

03

It is one dimension

"Great at research, bad at writing, overcharges, fights refunds" collapses into a single number. Terms cannot be set from that.

04

The buyer forgets

Agents restart stateless. Even a bad experience is gone next session, so the same provider is rehired at flat terms.

100

Public score of a provider we control, written by ourselves on ERC-8004 with two $0.01 jobs from a wallet we own. Agent 84571 on Base. At a cent a job no alarm fires; at scale an autonomous buyer bleeds on repeat failures.

How it works

One hire, end to end.
Memory sits between the broker and the chain.

A Python memory service is the only writer of the Sibyl Memory store. Node brokers are HTTP clients of it and hold no ranking, pricing or terms logic of their own. Every hire is a loop through memory, Virtuals ACP and Base.

01 decide

Rank from memory

Private score, live failures in this category and the consortium signal decide who is hirable. Public score is a tie-break, never the answer.

02 terms

Status sets the leash

Unknown: staged 2x, evaluator required, one retry, 10 % escrow cap. Trusted: single stage, no evaluator, two retries, cap up 35x.

03 hire

Create and fund on ACP

Job created by offering name or raw requirement, funded up to the memory-set max price. Every transaction lands on Base.

04 evaluate

Score against the stored spec

The REFERENCE tier holds the acceptance criteria. 5/5 releases escrow, a miss rejects and observes the refund.

05 remember

Journal, promote, signal

One journal event per job. Three samples or two failures promote a warm entity, rewritten in place. A redacted signal goes to the consortium.

06 publish

One honest vote on ERC-8004

The evaluator score goes back on chain with a chain-bound commitment hash, so the public number gains one verifiable opinion.

Trust vector

Trust is a vector between two agents,
not a number everyone shares.

Four behaviours are tracked per counterparty and per category, learned only from jobs this buyer ran, smoothed with an EWMA and decayed with a 14-day half-life. Status follows from the vector; terms and price follow from status.

Every write is rewritten in place: one row per counterparty, updated after every job, no append-only history to grow stale. The journal keeps the per-job evidence, the entity keeps the verdict.
The deletion test

Without memory GRUDGE is not weaker.
It is nothing.

There is no fallback formula. scripts/deletion_test.sh runs three phases against a temporary database and the broker's behaviour collapses exactly where memory is removed.

PHASE 1 · MEMORY UPRefuses the provider that burned it and names the job.
PHASE 2 · SERVICE STOPPEDCannot rank, price or set terms. Exits with code 3. No decision.
PHASE 3 · DATABASE WIPEDThe grudge is gone. Hires the burned provider again, at stranger terms.
